# 11. レート計算・試合結果保存（TASK-28）

仕様: [Notionタスク](https://app.notion.com/p/3f3df60d211481b49ce9d8f54dd8d0f3)・[設計書 §8–9](https://app.notion.com/p/043a2936051c43c89fdb2f423a15ee4e)。
PR #13 の補正済み順位を入力に使う。実装を、配点、DB保存、再処理と結果画面、検証の4項目に分ける。

## 配点（placement-elo-v1）

2026-10-15の相談を反映し、設計書の「1位 +30〜40」を変更。「下位でも下げ幅を小さくする」を主目的にする。
同格100人・同順位なし・全員順位対象の基準：

|順位|変動|
|---|---:|
|1|+20|
|10|+8|
|30|±0|
|50|−2|
|70|−5|
|100|−8|
|フライング・未入力|−8|

初期値は1500、下限0。ゲスト・ボット本人のレートは更新しない。
参考記録（成功だが計測不足・不安定で順位なし）は本人の変動0、相手の評価からも除く。
フライング・未入力は有効記録より下位として相手の評価に含める。

### 数式

本人 i に対する相手 j の期待勝率 `Eij = 1 / (1 + 10^((Rj-Ri)/400))`。
参考記録と本人を除く相手全員の平均を `E` とする。
`N` は相手の人数、`W` は自分より下位の人数、`T` は同順位の相手人数。
有効記録の評価順位 `p = 100 - 99 × (W + T/2) / N`。
同順位は占有順位の中央で評価する。全員同タイムで全員に1位報酬を与えない。
相手が一人も評価対象にならなければ変動0。

順位基礎点 `B(p)` は (1,20)、(10,8)、(30,0)、(100,−8) を結ぶ折れ線。
`B >= 0` なら `B × 2 × (1-E)`、`B < 0` なら `B × 2 × E` を使う。
これを [−8,+28] に制限し、四捨五入（ちょうど半分は0から遠い側）する。
フライング・未入力は相手の強さによらず−8。保存する更新後レートは `max(0, before + delta)`。
表示する増減は保存された `after-before` とするため、下限付近で実際より大きな減点を表示しない。

### ボット・ゲスト・長期変動

現行のボットは全て同じ生成分布（成功時180–900ms、5%フライング、3%未入力）なので、期待値計算用の強さを全て1500に固定する。ゲストは実力を継続推定しないため、相手としては1500を使う。ゲストの個人レートを作る意味ではない。
ボット比率による報酬係数は設けない。同じ強さ・同じ結果なら人間100人でもボット混在でも同じ配点。

通常のEloのようなゼロサムではなく、平均レートの一定性は保証しない。
固定1500のボットからの加点は本人レート上昇とともに縮小し、十分な差があると丸めにより0になる。
正の固定加点を足し続ける方式は使わない。下限0・加点上限28・減点上限8も設ける。
ボット1500の実力校正は暫定。実運用では人間のみの平均・中央値、ボット比率別の変動を調べて調整する。
係数は `internal/results/rating.go` に集約し、変更時は formula version を上げる。過去の保存済み結果は再計算しない。

## DB・二重更新防止

- `users.rating`: 現在の整数レート、初期1500。
- `matches`: 試合UUID、ルームUUID、結果確定・保存時刻、配点版、入力のSHA-256。
- `match_results`: 試合・参加者ごとの結果、表示名、区分、順位、補正後時間、更新前後レート。
- 主キー `(match_id, participant_id)` と一意制約 `(match_id, user_uid)`、外部キー・CHECK制約で重複や不正な組合せを防ぐ。
- ゲスト・ボットは `user_uid` とレートをNULLで保存。Firebase UIDをWebSocketや結果APIに露出しない。

試合100人分を検証した後、1トランザクションで試合IDをINSERT。既存IDなら入力ハッシュを照合し、同じ内容に限り保存済みレートを返す。
新規試合では登録ユーザーをUID順に `FOR UPDATE` でロックし、その時点のレートで全員を計算、100人分の結果とレートを保存してCOMMITする。
同じユーザーが別試合を並行処理しても更新を失わない。保存順で直列化し、試合終了順への並べ直しはしない。
途中失敗は全てロールバック。COMMITの応答だけ失われても同じIDの再処理で二重更新されない。
再処理時に参加者・結果・ユーザー対応が変わった同一IDは拒否する。

### マイグレーション

サーバーは自動適用しない。既存の001を適用済みのDBに、起動前に002を適用する。
既存環境の接続設定を確認し、ルートから実行する：

```sh
docker compose exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < backend/migrations/002_match_results.sql
```

002はトランザクション内でDDLを実行し、同じファイルの再適用が可能。
旧サーバーは追加カラム・テーブルを参照しないため、コードのロールバック時はデータを保持する。自動DROPはしない。

## 保存失敗・画面・再処理

判定完了時に `finished` と `persistence: pending` を通知。順位は表示できるが、レートは未確定と表示する。
DB処理はルームのmutex外で実行し、1回5秒で打ち切る。失敗すると `retrying` を通知し30秒ごとに同じ入力で再試行する。
再試行対象はクライアントが退出・再戦しても保持し、保存成功から2分後にルームを解放する。
未保存ルームも既存の最大1000ルーム制限に数え、無制限にメモリを増やさない。

保存成功で `saved` と更新前後レートを通知。結果画面ではWebSocket退出後も認証付き `GET /api/matches/{id}/rating` を3秒間隔で確認する。
APIは本人のレートのみ返し、未参加者は404。認証なしは401。保持済み情報がなくDB取得に失敗した場合は503。
HTTP確認は10秒でタイムアウトし、通信失敗を表示して再試行する。404は再起動・期限切れの可能性を表示して自動確認を止め、手動の再確認ボタンを出す。
登録ユーザーは保持期間後もDBから自分の保存済み変動を取得できる。ゲストはDBに認証IDを残さないため、取得はルーム保持期間内のみ。

**制限:** 未保存ジョブはメモリ内で、プロセス停止・再起動を跨ぐ永続キューではない。DB障害中にサーバーを再起動すると未保存結果は失われる。画面は未保存を表示し、保存済みとは扱わない。停止時は未保存の試合IDをエラーログへ残す。保存完了を待って計画停止する運用が必要。
保存失敗ログには試合ID・試行回数と安全なエラー分類/SQLSTATEを残し、接続文字列や生のDBエラーメッセージは出さない。
戦績一覧・全体ランキング・タイトルのプロフィールレート取得は後続タスク。今回接続するのは試合結果の確定レート。

## 検証

使い捨てDBの `TEST_DATABASE_URL` を指定し `go test -race ./...`。
DBテストは独立スキーマを作成・削除する。開発DB・本番DBには実行しない。

- 配点の1/10/30/100位、強弱補正、ボット混在、同順位、参考記録、ゲスト、失敗、加点上限、固定ボットからの加点縮小。
- PostgreSQLで同一試合10並列再処理、100行のみ保存、異なる内容の同一ID拒否、末尾行のINSERT失敗で全結果・レートのロールバック、復旧後の再保存、重なるユーザーの別試合並行更新、レート下限。
- 保存中でも別ルームに参加できる、明示退出後の保存、再試行、ゲスト・本人・部外者のアクセス制御、停止時のキャンセル。
- フロントで保存前・再試行中・保存後・ゲスト・取得期限切れを確認。

自動テストは実Firebaseアカウント・実回線のブラウザ通し確認を代替しない。

保存待ちでも試合終了からretention後にルームと所属を解放する。保存状態は別マップに保持し、終端状態からretention後に取得時／次の保存開始時に削除する。恒久エラー（入力不正・内容衝突・ユーザー不存在）は直ちにfailed、一時エラーも最大10回でfailedになる。failedでは自動ポーリングを停止する。サーバー再起動で未保存ジョブは失われる。ゲストのみの試合も確定結果として保存するが、ゲストのUIDとレートは保存しない。
