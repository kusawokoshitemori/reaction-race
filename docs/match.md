## 状態と通信

既存の認証済み `/api/lobby` 接続を試合終了まで使う。
`waiting → locked → ready → signal → settling → finished`。
全員フライングした場合は ready から settling へ進む。

- locked: 100人確定。1秒後にreadyへ。
- ready: 合図待ち。2〜5秒のランダム待機（暫定）。入力はフライング。未来の合図時刻は公開しない。
- signal: サーバーが実際に状態を切り替えた時刻をsignalAtに記録。締切はその3秒後。
- 全員入力済み（フライングを含む）、または締切でsettling。未入力はno-record。
- settling: 結果区分を固定。3秒間の試合後RTT計測を行い、補正と順位を確定してfinishedを通知。
- finished: 結果を2分保持してからタイマー・ルーム・所属・接続を解放する。

クライアントの入力は `{"type":"tap"}` のみ。UID、反応時間、ルームIDは受け付けず、認証済み接続から参加者を決める。入力済み通知は完全スナップショットの `input` に含めるため、低速接続で中間通知が集約されても最新の受付確認を復元できる。

既存room通知に以下を追加する:

- `you`: 接続本人の公開participant ID（待機中も送信）
- `matchId`: 試合ID
- `signalAt`: 合図のUnixミリ秒（合図前は省略）
- `input`: 本人の確定入力。participantId、outcome、receivedAt、reactionMs
- `results`: finished時のみ、確定した全参加者の結果（名簿順）

締切は排他的で、ちょうど3秒の入力も期限外。受付判定の直列化点はmutex取得直後のサーバー時刻取得。タイマーも同じmutexを使い、先に確定した結果を後続の入力やタイマーが書き換えない。WebSocketメッセージ取得後、JSON解読・DB処理・順位計算より前に時刻を記録する。ネットワーク到着からこの直列化点までの待ち時間は補正していない。

ボットは既存生成器を使用し、フライング・成功・未入力を生成。成功入力は実際のsignalAtからのオフセットで予約する。ボット時刻はサーバーが生成した予定時刻であり、人間の受信時刻とは区別する。待機後の切断・明示的退出でも確定名簿は保持し、試合は続行する。明示的退出は所属を解放し、予期しない切断は再joinで現在状態・本人入力・確定結果に復帰する。

## 画面

合図と結果はサーバー通知でのみ切り替える。クリック／タップ／Spaceで一回送信し、受付確認を待つ。ヘルプ表示中、フォーム操作、キーリピートでは送信しない。接続障害時は再試行できる。結果画面には実際の100人の結果区分と補正後の時間・順位を表示する。補正不能な時間は参考記録として順位対象外にする。

RTT・遅延補正・順位の仕様は[09の実装](latency-correction.md)を参照。レート計算とDB保存は未実装で、レートは未更新として表示する。再起動でメモリ内の試合・結果は失われる。

## ログと検証

`match ready / signal / input accepted / settled / finished` にroom_id、match_idと判定情報を記録。入力拒否はDebugログにreason（duplicate / late / not_accepting）を残す。トークン、チケット、Firebase UID、表示名は記録しない。
